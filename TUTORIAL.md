# TUTORIAL

A layer-by-layer walkthrough of how KardIQ actually works, written against
the real implementation - not an aspirational description. Read
[`README.md`](README.md) first if you just want to run it.

## 1. The user journey

A learner opens the frontend, types a question like *"How does LangChain
connect to OpenAI?"*, and gets back an answer, a list of source cards, and
an expandable panel showing exactly which tools ran and how long each
took. If the system has no relevant cards or relationships for the
question, it says so explicitly instead of making something up.

## 2. Request flow

See [`docs/diagrams/sequence.md`](docs/diagrams/sequence.md) for the full
sequence diagram. In short: **frontend → agent → MCP server →
{card-service, graph-rag} → {PostgreSQL, Neo4j}**, and back up the same
chain. A single `X-Request-Id`, generated by the frontend, is forwarded
through every hop and shows up in every service's logs and in the agent's
returned trace - so a real answer can always be traced back through every
component that produced it.

## 3. Frontend (`apps/frontend`)

Next.js 16, App Router, TypeScript strict. `src/api/agentClient.ts` is the
*only* place that makes a network call - it always targets
`NEXT_PUBLIC_AGENT_URL`, never an internal service. `app/page.tsx` owns
all state (`loading`/`result`/`error`) and orchestration; everything else
is a small presentational component: `ChatForm`, `AnswerPanel`,
`TraceInspector` (the "compact inspectable panel" that shows provider,
model, request id, and every tool call's outcome), `ErrorBanner`,
`LoadingIndicator`. `NEXT_PUBLIC_AGENT_URL` is inlined into the client
bundle at **build time** - changing it means rebuilding the image, not
just restarting the container.

## 4. Agent (`services/agent`)

FastAPI + LangChain. `AgentService.chat()` runs a fixed, deterministic
pipeline - no autonomous loop:

1. `GET /tools` on the MCP server (tool discovery, kept in the trace even
   though the pipeline below always calls the same tool).
2. `POST /tools/graph_search/call` with the raw user message as the
   query.
3. If the returned `contextText` is empty, skip the LLM entirely and
   return a fixed "not enough context" answer.
4. Otherwise, call the LLM (`llm/guardrails.py`) with a system prompt that
   only allows it to answer from that context.
5. Return the answer plus the full trace.

`llm/llm_factory.py` builds a `ChatOpenAI` or `ChatGroq` client based on
`LLM_PROVIDER`, failing fast at startup if that provider's API key is
missing. `llm/guardrails.py` enforces `LLM_REQUEST_TIMEOUT_SECONDS` /
`LLM_MAX_OUTPUT_TOKENS` (via the client's own settings) and retries
transient `429`/`5xx` provider errors up to `LLM_MAX_RETRIES` times with
backoff - timeouts and non-retryable failures become a structured
`LlmGuardrailError` in the `/chat` response, never an unhandled 500.

## 5. MCP server (`services/mcp-server`)

An **HTTP adapter**, not the official MCP stdio/SSE protocol - see
[`services/mcp-server/README.md`](services/mcp-server/README.md) for why.
`tools/registry.py` is a single explicit dict of the four required tools
(`list_cards`, `create_card`, `graph_search`, `health_report`), each with
a Pydantic input/output schema. `POST /tools/{name}/call` validates
arguments, runs the tool's handler, and always returns HTTP 200 with
`{tool, success, result|error, downstream, requestId}` - a genuinely
unknown tool name is the only case that returns 404, since that's a
routing error rather than a tool failure. Every downstream call
(`clients/card_service_client.py`, `clients/graph_rag_client.py`) has a
timeout and normalizes 4xx/5xx/timeouts/connection failures into one
`DownstreamError` type.

## 6. Card service (`services/card-service`)

Spring Boot 4, Java 26, Gradle. Layered `api` / `application` / `domain`
/ `infrastructure` packages; the `Card` JPA entity never crosses the REST
boundary directly - `CardMapper` (MapStruct) converts to/from
`CardRequest`/`CardResponse` records. `POST/GET/PUT/DELETE /api/v1/cards`
under Bean Validation, with a shared `ApiError{code, message, requestId,
timestamp}` shape from `GlobalExceptionHandler`. `RequestIdFilter`
extracts (or generates) `X-Request-Id` into SLF4J's MDC, so
`CardServiceImpl`'s create/update/delete logs automatically carry it.

## 7. PostgreSQL

The **source of truth** for cards - owned exclusively by card-service.
Schema and seed data are Flyway migrations
(`src/main/resources/db/migration/`): `V1` creates `cards` and
`card_tags`; `V2` seeds the `LangChain` and `OpenAI` demo cards with fixed
UUIDs (`1111...`, `2222...`) so graph-rag and `scripts/seed-data.sh` can
reference them deterministically. `hibernate.ddl-auto: validate` - Flyway
owns schema changes, Hibernate never generates DDL at runtime.

## 8. Graph RAG (`services/graph-rag`)

FastAPI + the Neo4j Python driver. `repository/graph_repository.py` is the
only place Cypher lives, and every query is parameterized. Retrieval
(`services/retrieval_service.py`) is deliberately simple, per its own
`CLAUDE.md`: extract keywords from the (possibly full-sentence) query,
keyword-match card title/body/tags, expand one hop via `RELATED_TO`,
rank exact title/tag matches above body-only matches, and format a
`contextText` string - no embeddings. `POST /graph/cards` and
`/graph/relations` are MERGE-based upserts, so `seed/seed_demo_data.py`
(run automatically when `SEED_ON_STARTUP=true`, the default) and
`scripts/seed-data.sh` are both safely re-runnable.

## 9. Neo4j

A **retrieval index, not a second source of truth** - owned exclusively
by graph-rag. `Card` nodes mirror `id`/`title`/`body`/`tags`/`updatedAt`
from Postgres (synced via graph-rag's API, never by reading Postgres
directly); `RELATED_TO` edges carry a `label` (e.g. `"USES"`), `weight`,
and `createdAt`. See
[`docs/diagrams/data-ownership.md`](docs/diagrams/data-ownership.md).

## 10. Container runtime

Every component owns its own `Dockerfile` (see
[`infra/docker/README.md`](infra/docker/README.md) for why they aren't
centralized). The root `docker-compose.yml` wires all 7 pieces with
`depends_on: condition: service_healthy` chained in dependency order and
service-DNS names everywhere *except* the frontend's build-time agent URL
(the browser runs on the host, not inside the Docker network, so that one
has to be `localhost`, deliberately). Two non-obvious fixes worth knowing
if you touch these images: card-service's and the frontend's base images
already ship a uid-1000 user (so don't `useradd --uid 1000`), and Next's
standalone server binds to `$HOSTNAME` if Docker has set it - the
frontend Dockerfile explicitly overrides it to `0.0.0.0`.

## 11. Kubernetes (`infra/k8s`)

One Deployment + Service per component, `replicas: 1`, applied in
dependency order by `scripts/k8s-apply.sh`. A shared `kardiq-config`
ConfigMap and `kardiq-secrets` Secret are injected via `envFrom` into the
four app Deployments (simpler than one ConfigMap/Secret per service, at
the cost of each pod seeing a few env vars it doesn't use - see
[`infra/k8s/README.md`](infra/k8s/README.md)). Every Deployment sets
`enableServiceLinks: false`: without it, Kubernetes auto-injects
`<SERVICE>_PORT`-style env vars for every Service in the namespace, which
corrupted Neo4j's own `NEO4J_`-prefixed config-from-env mechanism during
testing (`NEO4J_PORT_7687_TCP_PORT` got parsed as a bogus config key).
Images are referenced by their local `docker compose build` tags with
`imagePullPolicy: IfNotPresent`, which works out of the box against
Docker Desktop's built-in Kubernetes (and `kind`/`minikube` with an image
load step) - see the same README for pointing this at a real registry.

## 12. Tests

- **Frontend:** Vitest + React Testing Library - the API client (mocked
  `fetch`), every component, and a page-level integration test covering
  loading/success/chat-error/network-error states with real rendering.
- **Agent / MCP server / graph-rag:** `pytest`, no real API keys or
  running services required - downstream HTTP clients are tested against
  `httpx.MockTransport` or hand-written fakes; the agent's guardrails are
  tested against a fake chat model that raises fake provider exceptions.
- **Card service:** JUnit 5 - unit tests with Mockito, `@WebMvcTest`
  controller tests, and Testcontainers-backed repository/full-context
  integration tests (needs Docker).

Run everything with `scripts/test-all.sh`, which skips (with a clear
message) whatever prerequisite isn't installed rather than failing
opaquely.

## 13. Extension points

- **More graph RAG sophistication:** embeddings, multi-hop expansion, or
  a real full-text index - graph-rag's own `CLAUDE.md` deliberately
  defers this until the simple keyword approach is proven insufficient.
- **Multi-turn conversation:** `ChatRequest.sessionId` is already an
  opaque passthrough field in the agent's API, logged but not yet used to
  maintain conversation state.
- **More MCP tools:** add a new module under `services/mcp-server/app/tools/`
  following the existing four as a template, and `register()` it - the
  registry and `/tools` listing pick it up automatically.
- **A second LLM provider:** `llm_factory.py`'s provider switch is the
  only place that needs a new branch.
